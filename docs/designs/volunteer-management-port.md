## Problem Statement
The 2026-27 FBLA Coding & Programming topic is "Serving the Community: Nonprofit Volunteer
Management": help nonprofits recruit, organize, and manage volunteers and service activities,
coordinate volunteers, manage opportunities, maintain records, and monitor participation, for
both volunteers and organization leaders. Judging is a 110-point rubric that rewards language
rationale, comments, modular design, UX + accessibility, intuitive navigation with an
interactive help menu, an intelligent feature (Q&A, recommendations, smart filters), syntactic
+ semantic input validation, full prompt coverage explained in the instructions, customizable
reports for data analysis, and appropriate data structures.

Last year's app (Trove, `russy457/fblaslc2026`, ~35k lines of React/TS/Firebase) already has
most of the machinery the rubric rewards: PDF report builder, in-house search engine, AI help
center, onboarding tour, Turnstile bot check, auth, rules, tests, CI. The job is to carry all
of it into this repo, re-targeted at volunteer management, fix the errors it shipped with, and
add the features the new prompt needs.

## What Makes This Cool
- **One loop, three devices, twenty seconds.** The coordinator's laptop shows the live roster.
  A tablet sits in kiosk mode. A volunteer checks in on their phone with a code, and the roster,
  attendance rate, and hour totals update live on the laptop. That is the whole volunteer-to-
  leader loop in one demo beat, and it uses the rubric's 3-device limit as a feature.
- **AI shift planner.** A coordinator types "need 12 people Sat 9-1 sorting at the food bank".
  The app drafts a validated opportunity and ranks the best-matched volunteers (skills,
  interests, availability, distance, reliability), ready to invite.
- **Hours you can trust.** Volunteers download a service-hour verification letter (PDF) with a
  unique verify code. Anyone (an NHS sponsor, a counselor) can check it on a public `/verify`
  page. Paper hour logs get lost and signatures get faked; this fixes that.
- **Waitlist + reliability.** Full shifts take a waitlist that auto-promotes on cancellation.
  Each volunteer carries a reliability score (attended vs. no-show) that coordinators see and
  reports chart over time. Industry data says about 1 in 4 scheduled volunteers cancel or
  no-show, so this targets the most expensive failure in volunteer programs.

## Landscape (search, 2026-10-06)
- Common features across VolunteerHub, Galaxy Digital, Better Impact, Bloomerang Volunteer:
  shift scheduling, profiles, onsite check-in, hour tracking, skills matching, exportable hour
  logs for grants/boards.
- Failure modes: tool sprawl and signup friction (every extra signup step loses people), about
  1 in 4 no-show/cancel, about 30% of volunteers don't return after year one (often citing
  disorganization), paper hour verification is lost or falsified.
- Implication: one-tap signup, waitlist auto-fill, reliability, and verifiable hour records
  are where this app can stand out, and they double as presentation talking points.

### Behavior spec

**Backend placement.** Anything that must be trusted (check-in/out, signup and waitlist
changes, hours letters, AI calls) runs in Cloud Functions with Firestore transactions. Plain
reads and owner-only edits stay client-side under Firestore rules. Consequence: the team's new
Firebase project must be on the Blaze plan (free quota covers this usage; Blaze needs a billing
card on file). Local development runs the Functions + Firestore + Auth emulators under a
`demo-fbla2027` project id.

**Roles and authorization.**
- `volunteer`: every signed-in user.
- `owner` / `coordinator`: membership docs at `organizations/{orgId}/members/{uid}` with
  `role`. Any signed-in user with a verified email can register an org and becomes its
  `owner`. Owners invite coordinators with a single-use invite code (expires in 7 days).
  Coordinators manage opportunities, roster, check-in kiosk, hours approval, and no-show
  overrides for their org only. Owners also edit the org profile and manage members.
- `admin`: Firebase custom claim `admin: true`, set by a documented one-off script with a
  service account (replaces last year's hardcoded uid). Admins verify orgs (EIN format plus
  manual check) and moderate the impact-stories feed.
- New orgs start `verified: false` and show an "Unverified" badge until an admin verifies.
- Rules matrix, enforced in `firestore.rules` and covered by rules tests:

| Collection | Read | Create | Update | Delete |
|---|---|---|---|---|
| organizations | public | verified-email user (sets self as owner) | owner (not `verified`); admin (`verified`) | owner |
| organizations/{id}/members | members | owner via invite redemption Function | owner | owner |
| opportunities, instances | public | org coordinator | org coordinator (not counts) | org coordinator |
| signups | the volunteer; org coordinators | Function only | Function only | none |
| hoursLogs | the volunteer; org coordinators | volunteer (manual, `pending`) or Function | coordinator (status) | none |
| verifications | `get` by exact id only, public; `list` denied | Function only | Function only | none |
| reviews | public | signed-in, has a completed signup at that org | author; coordinator (`response` only) | author |
| notifications/{uid}/items | owner uid | Function only | owner uid (`read` flag) | owner uid |
| users (public profile) | public, minor-safe fields | self | self | self |
| users/{uid}/private | self | self | self | self |

**Signup, capacity, waitlist.**
- Signup and cancel are callable Functions that run one Firestore transaction on the
  opportunity instance: read `signupCount`, `capacity`, and the ordered `waitlist` array of
  uids, then write the signup doc (`{instanceId}_{uid}`, so duplicates are impossible) and the
  counters. Rules block clients from writing counters, so overbooking can't happen under
  concurrent signups.
- When full, a new signup goes to the end of `waitlist` (waitlist cap = capacity).
- On cancel, the same transaction pops the first waitlisted uid and auto-confirms them (no
  accept step), then writes them a notification.
- Promotion cutoff: no auto-promotion within 2 hours of start; the freed slot opens for normal
  signup instead.
- Min age is enforced in the signup Function against the volunteer's private birth date.

**Recurring opportunities.** A recurring opportunity is a series doc with a weekly rule plus
materialized per-date instance docs (next 8 weeks, extended when a coordinator opens the
dashboard). Capacity, waitlist, signup, check-in, and hours all live on the instance.
"Sign up for the whole series" is a convenience that creates one signup per future instance.
Times are stored as UTC ISO strings plus the org's IANA time zone and displayed in the org's
zone with a zone label.

**Check-in kiosk (the 3-device demo).**
- Direction: the kiosk shows a code, and the volunteer types it on their own phone.
- A coordinator starts kiosk mode for one instance. The kiosk fetches a 6-digit code from a
  coordinator-only Function every 30 seconds. The code is an HMAC of a server-held
  per-instance secret and the 30-second window, so it can't be computed client-side and a
  photo of it expires fast.
- The `checkIn` Function accepts a code for the current or previous window only, only from 30
  minutes before start until the scheduled end, only for a volunteer with a confirmed signup,
  and only once per signup (repeat calls are idempotent no-ops).
- Kiosk mode is a locked route: it shows the code, the live checked-in count, and an
  AnimatedList of arrivals, with no links to other coordinator screens. Exiting requires the
  coordinator to re-enter their password (Firebase re-authentication). Limitation: the
  coordinator's session is still active underneath; documented as acceptable for a supervised
  device.

**Check-out and hours.**
- Status flow: `confirmed` -> `checked-in` -> `completed`; `confirmed` -> `no-show`;
  `confirmed`/`waitlisted` -> `cancelled`.
- Check-out uses the same kiosk code flow. Hours = check-out minus check-in, clamped to
  [0, scheduled length + 30 min], rounded to the nearest 0.25 h.
- Forgotten check-out: one hour after the scheduled end, a scheduled Function closes the
  signup at the scheduled end time and marks the HoursLog `needsReview`.
- Kiosk-verified hours are auto-approved. Volunteer-submitted manual hours (service done off
  the platform) and `needsReview` logs require coordinator approval. Approval or rejection
  sends a notification.

**No-show and reliability.**
- One hour after the scheduled end, a scheduled Function marks confirmed signups that never
  checked in as `no-show`. A coordinator can change it to `excused`.
- Cancellations 24+ hours before start don't count. Later ones are `lateCancel`.
- Reliability over the volunteer's last 20 finished signups =
  attended / (attended + noShows + 0.5 x lateCancels), shown as a percent.
- Cold start: under 3 finished signups shows "New volunteer" with no number, and match
  ranking uses a neutral 0.8.
- Volunteers see their own score and the signups behind it, and can send a "please review"
  note to the coordinator, who can excuse the item.

**Verified hours letters and /verify.**
- Letters are issued only by a Function, only from `approved` HoursLogs, for a volunteer-chosen
  date range and org filter.
- The verify code is 128 bits from `crypto.randomBytes`, base32-encoded, and is the
  `verifications/{code}` doc id. Rules allow `get` by exact id and deny `list`, so codes can't be
  enumerated and are infeasible to guess. App Check further limits scripted traffic once
  enabled.
- The public page shows only: first name + last initial, organization name(s), total approved
  hours, date range, issued date, and status (`valid`, `superseded`, `revoked`). No school,
  birth date, contact info, or location.
- A Firestore trigger marks any letter `superseded` when an HoursLog it counted changes status
  or hours. The page always shows the authoritative totals, so an edited PDF doesn't match.

**Notifications.** In-app only: `notifications/{uid}/items` with a live listener and a bell
menu. Events: waitlist promotion, hours approved/rejected, shift-planner invite, letter
superseded, and shift reminders (generated client-side when the app opens within 24 hours of
a confirmed shift). Email and push are out of scope for the port.

**AI features (shift planner and Q&A).**
- All model calls go through a Cloud Function holding the API key as a Functions secret
  (`.secret.local` for the emulator, gitignored). No AI key is ever a `VITE_` variable.
- Default provider is Anthropic Claude (model id configurable by env); provider choice stays
  open for the team.
- No-key path, Q&A: the help center answers by searching help articles with the in-house BM25
  engine and shows the top articles.
- No-key path, shift planner: a deterministic parser extracts count, day/date, time range, and
  cause keywords from the sentence and prefills the structured opportunity form. Volunteer
  ranking is always deterministic (match score), so it works with or without AI. With a key,
  the AI improves the parse and writes the opportunity description.

**Privacy and minors.**
- Minimum account age 13, checked against birth date at signup (COPPA). Birth date lives in
  `users/{uid}/private`, readable only by the user; Functions use it for min-age checks.
- Public profile defaults for under-18: display name as first name + last initial, avatar,
  badges, total approved hours, orgs helped. No school, city, or birth date. Adults can opt in
  to showing more. Coordinators see full name and contact only for their own org's signups.
- Volunteer location is stored as a coarse geohash (precision 5, about 5 km), never an exact
  address. Org addresses are public.

**Maps and geocoding.** Mapbox with a public `pk.` token from env, URL-restricted to the
deployed domain and localhost. Without a token: maps are hidden, org coordinates come from
seed data, and volunteers set location from a bundled demo ZIP-centroid lookup or
optional browser geolocation.

**Demo topology.** Primary: deploy to the team's new Firebase project (Hosting + Functions)
before the first competition round, and rehearse the 3-device beat on that URL. Fallback: LAN
emulator mode (emulator host from `VITE_EMULATOR_HOST`, Vite dev server on `--host`, devices on
the laptop's own hotspot to avoid venue client isolation), documented step by step in
`docs/DEMO.md` and rehearsed once.

**Old repo secrets.** Not porting them is not enough. The team revokes the Mapbox `sk.` token
and rotates the OpenRouter key and Turnstile secret in last year's accounts, and retires the
old Firebase project or restricts its API key. CI adds a gitleaks secret scan.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

### R2-1 — consistency (blocking)

**Problem**

> Notifications says shift reminders are generated client-side when the app opens, but the rules matrix makes notifications/{uid}/items create 'Function only'. A client cannot write those reminder docs, so the two statements contradict.

**Remedy**

> Choose one: reminders are ephemeral UI computed from the user's confirmed signups (never stored in notifications), or a scheduled Function writes reminder items. Update the Notifications text and rules matrix to match.

### R2-2 — consistency (blocking)

**Problem**

> Org registration lets a verified-email user create an organization and become its owner client-side ('sets self as owner'), but the members subcollection create column allows only the invite-redemption Function. The owner's own membership doc, which every coordinator/owner rule depends on, has no permitted creation path.

**Remedy**

> Specify how the owner membership doc is created: org registration runs in a Function that writes the org and owner member doc together, or rules allow a self-owner member doc only in the same batch as the org create (checked with getAfter). Add that case to the matrix and rules tests.

### R2-3 — feasibility (blocking)

**Problem**

> Firestore rules cannot restrict reads to some fields of a document: a readable users doc returns every field. 'public, minor-safe fields' as a read rule is not enforceable, and the self-writable public doc could hold school, city, or full name for a minor, all publicly readable.

**Remedy**

> State that the public users doc contains only public fields and everything else lives in users/{uid}/private (or another restricted doc). Add write rules (or Function-only writes) that reject non-allowed fields, and enforce the under-18 field set at write time, with rules tests.

### R2-4 — completeness (blocking)

**Problem**

> Coordinators are promised a volunteer's full name and contact for their org's signups, but users/{uid}/private is readable by self only and the public doc holds only minor-safe fields. No data path gives coordinators those fields, so the roster and check-in cannot show them as designed.

**Remedy**

> Define the path: e.g. the signup Function copies a contact snapshot (full name, email/phone) into the signup doc, which only the volunteer and that org's coordinators can read; or a coordinator-only Function returns it. Document which fields are copied and that they follow the signups read rule.

### R2-5 — completeness (blocking)

**Problem**

> Birth date lives in users/{uid}/private, which the matrix makes self-updatable, and nothing says where the 13+ check runs. A user can create or later edit their birth date to pass an opportunity's min age, or to move out of the under-18 privacy defaults, so the min-age and minor-privacy protections can be bypassed.

**Remedy**

> Enforce the 13+ check in rules on private-doc create (or in an account-setup Function), and make birth date immutable after creation (update denied for that field, or changeable only through an admin/Function path). Add rules tests for both.

### R2-6 — completeness (blocking)

**Problem**

> Waitlisted volunteers are auto-confirmed with no accept step, up to 2 hours before start, and notified only in-app (email and push are out of scope). A promoted volunteer who doesn't open the app won't know, then gets an automatic no-show that lowers their reliability score and match ranking. The design is unfair to the users it is meant to serve.

**Remedy**

> Choose a policy: promotions within a set window (e.g. 24 h) of start don't produce a counted no-show (auto-excused), or promotion requires an accept within a timeout before the next person is offered the slot. State the rule in both the waitlist and reliability sections.

### R2-7 — completeness (blocking)

**Problem**

> Check-out reuses the kiosk code, but the only stated window is the check-in window (30 min before start until scheduled end), while hours clamp up to scheduled length + 30 min, which implies late check-outs. The doc also doesn't say how one code entry is told apart as check-in or check-out: repeat check-in calls are idempotent no-ops, yet the same code entered again by a checked-in volunteer could instead check them out early.

**Remedy**

> Define the check-out acceptance window (e.g. from check-in until scheduled end + 30 min, before the forgotten-check-out job runs), and make check-out a separate explicit action (its own button and Function) with a minimum gap after check-in or a confirmation step.

### R2-8 — completeness (blocking)

**Problem**

> R1-10 asked for a rules matrix per collection. The new matrix omits collections the design now relies on: coordinator invite codes, recurring series docs, the kiosk per-instance secret, impact stories (admin-moderated feed), follows, saved orgs/opportunities, and curated collections. Their authorization is undefined, and the 'rules tests cover every row' criterion would pass with them uncovered.

**Remedy**

> Add rows for every persisted collection (invites, series, impact stories, follows, saved items, collections, and any server-only secrets marked as no client access) and keep the rules-test criterion tied to the complete list.

### R2-9 — feasibility (blocking)

**Problem**

> The AI Function holds a paid API key on a Blaze project with a billing card, but the doc doesn't say who may call it (signed-in users, coordinators only for the shift planner, anonymous visitors for Q&A?) or how calls are limited. A public callable endpoint can be scripted to burn API credit and Firebase spend. App Check is only 'once enabled'.

**Remedy**

> Specify caller requirements per feature (e.g. shift planner: org coordinators only; Q&A: signed-in users), a per-user rate limit and a daily cap, max input/output size, and whether App Check is enforced on the deployed demo. Note budget alerts on the Blaze project.

### R2-10 — completeness (minor)

**Problem**

> Instances are materialized for 8 weeks and extended only when a coordinator opens the dashboard. 'Sign up for the whole series' covers only already-materialized instances, so later instances don't get series signups, and if no coordinator opens the dashboard, volunteers see the series run out.

**Remedy**

> Store a series-subscription record that new instances honor when materialized, or state that whole-series signup covers only the current 8-week window. Consider a scheduled Function for materialization.

### R2-11 — consistency (minor)

**Problem**

> Constraints still say 'no .firebaserc, no firebase init, no deploy', while Demo topology and Distribution Plan now require a deploy (Hosting + Functions) before the first competition round.

**Remedy**

> Reword the constraint as 'no init or deploy until the new project exists' and point to the deploy deadline.

### R2-12 — clarity (minor)

**Problem**

> The status flow omits transitions defined elsewhere: waitlisted -> confirmed (promotion), no-show -> excused, and how lateCancel is represented (a status or a flag on cancelled).

**Remedy**

> List the complete status set and transitions, including excused and the lateCancel representation.

### R2-13 — clarity (minor)

**Problem**

> The reliability formula doesn't say how excused items and early cancellations count toward the 'last 20 finished signups' window (excluded from the window, or counted as attended).

**Remedy**

> State that excused and early-cancelled signups are excluded from both the window and the formula (or whatever is intended).

### R2-14 — completeness (minor)

**Problem**

> Behavior when the waitlist is also full is unstated, and so is what happens to remaining waitlisted volunteers after the 2-hour promotion cutoff (kept, notified, or cancelled at start).

**Remedy**

### R2-15 — clarity (minor)

**Problem**

**Remedy**

### R2-16 — feasibility (minor)
